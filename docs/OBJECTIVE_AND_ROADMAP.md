# Objective and roadmap

## Objective

Build an assistant the group can use during Kingdom Death: Monster 1.5 play. A player should be able to ask a question, receive an explanation grounded in applicable rulebook and card evidence, open the supporting text or images, and understand missing evidence or ambiguity.

The project began as a searchable companion to a scanned rulebook. It has developed into a card-and-rule assistant requiring source selection, combined explanations, follow-up handling, and supported declines. Card collection, transcription, OCR, and wiki experiments serve that objective. Completing an acquisition method does not establish a finished product.

## Release direction

The longer-term direction is the group's 1.5 core game. The first release focuses on the Prologue, first settlement, first level 1 White Lion hunt/showdown, and the following settlement. Other editions, expansions, and later campaign coverage are outside this release. Cunning remains unverified and excluded from active work.

The [first-release checklist](RELEASE_CHECKLIST.md) now defines required coverage, contextual/excluded content, acceptance requirements, and release gates. Existing coverage remains a limited prototype; required source gaps and untested behavior keep those checklist items open. The whole core game must not be described as supported.

## Phases

| Phase | Work | Completion checkpoint |
| --- | --- | --- |
| 1. Define the release | Turn the core-game direction into required coverage and acceptance criteria. | Required rules/cards, exclusions, and evaluation criteria are explicit. |
| 2. Prove the answer process | Evaluate question → sources → explanation → citations, with follow-ups and missing evidence. | Fresh questions identify retrieval, evidence, and explanation failures. Material process failures are repaired and retested. |
| 3. Fill required coverage | Add evidence for the release checklist in priority order. | Required topics have reviewed text, image evidence, provenance, and interpretation limits. |
| 4. Evaluate the release | Test unfamiliar scenarios and neighboring unsupported cases. | Agreed acceptance checks pass; material errors are resolved and limits documented. |
| 5. Prepare group use | Verify protected access, phone use, source viewing, feedback, and launch identity. | The group can use the intended version and report problems during play. |
| 6. Validate and release | Use it during a game and resolve release issues. | The agreed scope works in play, with a maintenance backlog for later additions. |

Phase 1 has a defined release checklist. The [first baseline](../evaluation/2026-10-24-release-baseline/REPORT.md) ran in local and optional Sol modes. Its routing/table/follow-up failures have [targeted repairs and regression checks](../evaluation/2026-10-24-retrieval-regression/REPORT.md). Required coverage and broader process evaluation keep phases 2 and 3 open. Development reruns are not independent accuracy estimates. Findings may require another pass while retaining the release boundary.
